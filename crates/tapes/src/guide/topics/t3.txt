T3 CODE THREADS
  tapes show 'http://<host>:3773/<environment-id>/<thread-id>' --tail 20
  tapes list --t3 --global --limit 10

  T3 Code is a host: each of its threads runs on a provider whose own store
  holds the recording. To tapes a thread is a name for that native session, so
  wherever a session id or --exclude is accepted, a thread reference reads
  exactly what the native id reads. Accepted forms: a web link
  http(s)://<origin>/<environment>/<thread>, with any ?query or #hash; the app
  links t3-thread://v2/<environment>/<thread> and t3-thread://v1/<thread>, also
  inside <...>; and a bare argument exactly equal to a thread id. stderr
  reports the rewrite: Note: T3 thread <id> "<title>" is <harness> session
  <native-id>, adding the thread's other native sessions and whether T3 marks
  it deleted.

  list --t3 keeps only sessions a thread maps to, before --limit and with every
  other filter. An installed listing's session carries a JSON t3 object
  (thread_id, environment_id when known, title, and link, an app link any
  session argument accepts), and TITLE falls back to the T3 title when no title
  is recorded. The index covers the newest 10000 threads and says so when more
  exist; a session two threads ran belongs to the newer one.

  The store lives under T3CODE_HOME, or ~/.t3, and the sqlite3 program reads
  it read-only. Without a store a listing is unchanged and a bare id passes
  through; a store that cannot be read warns on a bare id and adds an
  unavailable entry to a listing. A link and list --t3 fail instead, and each
  failure names the thread and what it needs:
    another environment    the thread is on the machine serving that environment
    not in the T3 store    this store holds no such thread
    no T3 store            set T3CODE_HOME, or read on the machine that has one
    sqlite3 not available  install it to read the store
    no native session yet  the thread's run has not started
    runs on <driver>       tapes has no backend for that provider
    Claude subagent        run the printed tapes child <parent> --reference <agent>
  --remote leaves a reference for the replica's own store. --input and
  --native-store refuse a link and --t3, and do not look a bare id up.


ANTIGRAVITY ACP
  tapes list --global --t3 --harness antigravity
  tapes show <native-id> --harness antigravity --full
  tapes workset <native-id> --harness antigravity --bundle <directory>

  The provider profile is under
  userdata/providers/antigravity/<profile>/antigravity-acp in the T3 home.
  conversations/<id>.db corroborates the UUID in trajectory_meta.cascade_id.
  The native transcript is brain/<id>/.system_generated/logs/transcript_full.jsonl.
  The short transcript and chunks are alternate projections of that recording.
  Identity discovery needs the conversation database. Transcript pickup also
  needs the native JSONL, and fails explicitly if it is unavailable. Multiple
  profile databases for the same id refuse selection.

  The reader keeps visible messages, reasoning, tool calls, generic tool
  results, model selections and native token usage. The native JSONL supplies
  no call id for generic results. Recorded step status is kept per turn.
  `PLANNER_RESPONSE` and token-bearing `CHECKPOINT` compaction records sum as
  `summed-requests` under the excludes-cache, includes-reasoning convention;
  `CHECKPOINT` calls without a model name enter unattributed usage rather than
  being dropped or misattributed, and native monetary cost stays absent.
  `trajectory_metadata_blob` supplies the session's working directory when
  present so `--here` and `--project` scopes select Antigravity sessions
  directly. Failed or interrupted provider turns from T3 statev2.sqlite appear
  separately in the read notes, joined by exact provider identity. A provider
  switch keeps each native session independent. A T3 link follows the
  active-provider rule above. Recover an earlier provider session by its native
  id.

  A projected Antigravity child thread can have a task reference in place of
  a native session reference. Its exact launch run must belong to the
  parent's active Antigravity provider instance. For detached launches the
  parent descriptor names the child and its spawn step. The parent database
  step and the child's inbox must agree on the launch tool call ID, and both
  conversation databases must corroborate their IDs in the same profile.
  Parent worksets include children with that native evidence. Missing or
  conflicting evidence refuses the child link and is reported in the parent
  workset's lineage coverage. The T3 listing index uses provider-thread
  native references.

  Native Gemini CLI files live under ~/.gemini/tmp/<project>/chats.
  Its session-*.json and session-*.jsonl formats carry a sessionId in
  conversation metadata. The filename suffix is a short id. Gemini CLI
  sessions have no established binding to these Antigravity ACP recordings.
